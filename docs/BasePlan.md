## 1. 项目总览与设计范式

### 1.1 项目目标
从原始音频（WAV/MP3）端到端自动生成高质量、可玩的音游谱面，优先支持 **4K VSRG（垂直下落式音游）** ，后续扩展至 osu!std、Maimai 等模式，输出标准 `.osu` / `.ma2` 等格式文件。

### 1.2 核心范式转移（2026 视角）

| 维度 | 旧范式（2024前） | **新范式（2026实施）** |
|------|----------------|----------------------|
| **标注依赖** | 依赖 Tier 2-4 显式结构化标注（风格/声部/Pattern 字段） | **零显式标注**，依赖模型隐式理解 |
| **控制方式** | 人工填写 15+ 字段的 `SectionChartIntent` | 仅需 `难度等级(1-15)` + `参考谱面(可选)` |
| **学习方式** | 有监督学习（标注→谱面） | **自监督预训练** + **RL/DPO 偏好对齐** |
| **知识来源** | 专家规则 + 少量标注数据 | **百万级社区谱面**（osu!等）的海量隐式知识 |

> **核心公式**：`音频 → MERT隐式理解 → VQ-VAE谱面分布学习 → RAG风格迁移 → DPO手感优化`

## 3. 逐模块技术选型详解

### 3.1 Stage 0：多模态音频编码器

#### 3.1.1 主选方案：**MERT-v1-330M + 可训练 Adapter**

| 属性 | 规格 |
|------|------|
| 参数量 | 330M (约 1.3GB) |
| 输出维度 | 768 (第12层) / 1024 (第24层) |
| 输入规格 | 25Hz 帧率, 覆盖 5秒 上下文窗口 |
| 预训练数据 | 大规模音乐自监督 (MLM风格, 涵盖古典/流行/电子等) |
| 推理硬件 | T4 (FP16) 可实时运行 |

**优势**：
1. **音乐专用**：在音乐标签分类、节拍跟踪、和弦识别、流派分类等 MIR 任务上显著优于通用音频模型。
2. **层次表征明确**：研究表明浅层编码节奏/速度，深层编码旋律/语义，完美契合分层生成架构。
3. **经济高效**：330M 远比 7B 的 Qwen2-Audio 轻量，推理成本仅为后者的 1/20。

#### 3.1.2 辅助增强（可选）：**Demucs (HTDemucs) 声源分离**

- 输出：`{drums, bass, vocals, other}` 四轨
- 融合方式：分离后的每轨分别过轻量 MERT encoder，与主音频 embedding 沿特征维度拼接。
- 决策：**设为可选标志**。在高质量数据训练时开启；快速推理时可跳过，模型仍能通过注意力机制隐式学习声部分离。

#### 3.1.3 为什么不用 Qwen2-Audio？

- Qwen2-Audio 核心优势在于 **Audio-LLM 对话/描述生成**，而非提供高密度时间序列表征。其 7B 参数在仅需 embedding 的场景下属过度冗余，且输出特征并非为音乐生成微调最优。

---

### 3.2 谱面语义 Tokenizer（VQ-VAE）

#### 3.2.1 选型：**标准 VQ-VAE**

| 属性 | 建议值 |
|------|--------|
| 时间粒度 | 1 小节 (4/4拍, 以 BPM 动态对齐) |
| 码本大小 (Codebook) | **2048** (基础) / **4096** (精细) |
| 编码器结构 | 1D-CNN + Transformer |
| 训练数据 | osu! 谱面 50K+ 首 (无标注) |

#### 3.2.2 码本语义设计
每个 Code Index 表征该小节内的 **Note 集合模式**，包括：
- 密度等级 (稀疏/中等/密集/超高)
- 节奏型 (16分音阶 / 三连音 / 切分 / 重拍和弦)
- 手型倾向 (阶梯/交互/双押/长条)
- 键位空间分布 (左倾/右倾/居中/全键盘)

#### 3.2.3 为什么不用 FSQ？
- FSQ (Finite Scalar Quantization) 主要用于超低比特率 **音频波形压缩**（如语音编解码）。
- 谱面 Tokenizer 目标是 **语义模式抽象**，VQ-VAE 的离散码本天然对应“类型”概念，且 Transformer 自回归建模 VQ 离散索引的范式已是业界标准（如 VQ-VAE + GPT 用于图像生成）。

---

### 3.3 Stage 1：全局密度规划模块

| 属性 | 规格 |
|------|------|
| 架构 | 6层 Bidirectional Transformer |
| 输入 | `audio_emb` + `difficulty_embedding` + `RAG_style_emb` |
| 输出 | 每 4 小节（或 Section）的 `density_target (0-1)`, `energy_level`, `rest_probability` |
| 训练方式 | **自监督回归**。从 osu! 谱面自动计算上述统计量作为伪标签，无需人工标注。 |
| 损失函数 | Huber Loss (鲁棒性) + 相邻段落平滑约束 (TV Loss) |

> **作用**：解决 AR 模型“目光短浅”的问题，在生成 Pattern Token 之前为模型提供一张宏观“施工蓝图”，保证副歌高潮、前奏铺陈、尾奏收束的结构合理性。

---

### 3.4 Stage 2：Pattern 序列生成主干

这是系统最核心的生成引擎，需权衡质量、速度与开发成本。

#### 3.4.1 主选架构：**AR (Autoregressive) Transformer Decoder**

| 属性 | 规格 |
|------|------|
| 层数 | 12-16层 |
| 注意力头数 | 16 |
| 上下文长度 | 256 tokens (约 256 小节，覆盖 4-5 分钟曲目) |
| 训练方式 | Teacher Forcing + Cross-Entropy Loss |
| 条件注入 | Cross-Attention (audio_emb) + AdaLN (difficulty/style) |

**选择理由**：
- 与 VQ-VAE 构成完整的两阶段范式（离散化→自回归），业界验证最充分（如 VQ-VAE-2, DALL-E）。
- 百万级 osu! 数据足以支撑 AR 模型学习长程依赖。
- 调试工具链成熟（HuggingFace Transformers / Megatron-LM）。

#### 3.4.2 备选/未来升级方案：**Flow Matching (Rectified Flow)**

| 属性 | 规格 |
|------|------|
| 采样步数 | 4-8 步 (相比 AR 的 256 步逐 token 快 30-60 倍) |
| 训练稳定性 | 优于 DDPM，无需复杂噪声调度 |
| 验证案例 | PianoFlow (音乐表演生成), MR-FlowDPO (音乐对齐) |

**迁移时机**：当业务规模扩大，推理延迟成为瓶颈（如网页端实时预览）时，用 Flow Matching 蒸馏 AR 模型。

---

### 3.5 风格控制机制（RAG）

#### 3.5.1 选型：**Retrieval-Augmented Generation (检索增强生成)**

| 属性 | 规格 |
|------|------|
| 检索库 | 百万级 osu! 谱面 (按 BPM/流派/谱师/难度 索引) |
| 检索特征 | 音频 MERT Embedding + 谱面结构统计量 (密度曲线) |
| Top-K | 3 首 |
| 注入方式 | 将检索到的谱面 Token 序列作为 **Prefix** 或 **Cross-Attention Key-Value** 注入 Decoder |

#### 3.5.2 为什么不用 Contrastive Learning（对比学习风格编码器）？

- 对比学习需要大量“同一谱师”的标注对来定义正负样本，数据获取困难。
- RAG **无需训练**，且可解释性强（用户可以明确看到参考了哪首谱面）。
- 在符号音乐/音乐生成领域，RAG 已被证明在客观指标和主观听感上优于 LoRA 微调。

---

### 3.6 偏好对齐策略（DPO）

#### 3.6.1 选型：**DPO (Direct Preference Optimization)**

| 属性 | 规格 |
|------|------|
| 数据来源 | osu! 玩家评分 / Pass Rate / Play Count 埋点 |
| 偏好对构造 | Chosen = 高评分(≥4.5星) & 高Pass率；Rejected = 低评分(≤2星) |
| 微调目标 | 最大化 `log σ(β * (log π_chosen - log π_rejected))` |
| 基座模型 | Stage 2 AR 预训练模型 |

#### 3.6.2 为什么不用 RLHF（PPO）？

- DPO 不需要单独训练奖励模型（Reward Model），也不需要在推理时与环境交互（Rollout），训练成本仅为 RLHF 的 1/3。
- 在音乐生成领域（LeVo, MR-FlowDPO）已成功应用，能显著提升“音乐性”和“结构合理性”。
- osu! 的隐式反馈（Play Count）天然构成海量、免费的偏好数据集。

---

### 3.7 Stage 3 & 4：解码与后处理

| 模块 | 技术方案 | 说明 |
|------|---------|------|
| Token → Notes | VQ-VAE Decoder (轻量 MLP + 1D-CNN) | 将离散 ID 映射回精确的 `(time, lane, type, duration)` |
| 物理约束引擎 | **规则系统** (硬编码) | 限制单帧最大按键数 ≤ 2 (4K标准)，同手最小间隔 ≥ 70ms，禁止越界等 |
| 格式转换 | 自定义 Writer | `.osu` (osu!mania), `.sm` (StepMania), 未来扩展 `.ma2` |

> **关键原则**：AI 负责**创意生成**，规则引擎负责**物理安全与合法性**。两者解耦，保证 100% 可玩性（不生成人类无法击打的谱面）。

## 4. 训练数据策略与来源

### 4.1 数据集构成

| 数据源 | 预估量级 | 标注情况 | 用途 |
|--------|---------|---------|------|
| **osu! 官方/社区谱面库** | 100 万+ 首 | 包含 `.osu` + 音频 (MP3) | 主训练数据 (VQ-VAE + AR) |
| **StepMania / Etterna** | 5 万+ 首 | `.sm` 格式 | 补充 VSRG 变体 |
| **BMS (Be-Music Source)** | 大量 | 高精度 Note + BGA | 验证复杂谱面逻辑 |
| **合成数据 (DAW 生成)** | 可无限生成 | 完美标注 | 长尾场景覆盖 (如特殊拍号) |
| **DPO 偏好数据** | 百万级 | osu! 玩家评分隐式标签 | 偏好微调 |

### 4.2 自动化预处理流水线

```
原始 (.osu + .mp3)
  → Step 1: 解析 .osu → NoteEvent[] (清理乱码/非标准)
  → Step 2: 自动计算统计量 (密度、段落边界、BPM) → 用于 Stage 1 伪标签
  → Step 3: 音频切片 & MERT 离线预提取 Embedding (节省训练时算力)
  → Step 4: 构建 VQ-VAE 训练数据集 (音频 Emb + Note 序列)
  → 存入 HuggingFace Datasets / 本地 Parquet
```

### 4.3 关键数据管护原则
- **质量过滤**：只保留 3 星以上且 `play_count > 500` 的谱面（社区验证过的好谱）。
- **去重**：同一歌曲不同谱面视为独立样本（保留多样性）。
- **版权处理**：训练数据仅用于学术/研究目的，生成系统输出不包含原音频拷贝。

## 6. 风险评估与缓解措施

| 风险编号 | 风险描述 | 影响 | 缓解策略 |
|:---:|---------|------|---------|
| R-1 | MERT 冻结可能导致对特定曲风（如重型电子）表征不佳 | 生成谱面适配度下降 | 保留 Adapter 可训练参数；如严重，考虑微调 MERT 后 6 层 |
| R-2 | VQ-VAE 码本坍缩（Index Collapse） | 生成多样性丧失 | 采用 K-means 初始化；增加 Commitment Loss 权重；启用随机重启机制 |
| R-3 | osu! 谱面质量参差不齐，模型学到坏习惯 | 输出手感差 | DPO 偏好微调兜底；在预处理阶段严格过滤低评分谱面 |
| R-4 | AR 自回归推理速度慢（生成 1 首约 10-30秒） | 用户等待时间长 | 未来路径：蒸馏为 Flow Matching 模型（4步采样）；缓存常用曲风的 Prefix |
| R-5 | 规则后处理过度约束导致破坏 AI 创意 | 谱面机械无趣 | 规则仅做“红线”校验（物理不可达），不改变 AI 的键型排列逻辑 |
| R-6 | 不同游戏模式（4K/6K/osu!std）差异巨大 | 架构需大改 | **先攻 4K VSRG**，模式扩展视为独立适配工程（仅需重写 Tokenizer 和导出层） |

## 7. 分阶段实施路线图

### Phase 1：地基建设（0-3 个月）
- 搭建数据预处理流水线，完成 10K 首 osu! 谱面的 MERT Embedding 离线提取。
- 训练 **VQ-VAE Tokenizer** (码本 2048)，验证重建准确率 > 95%。
- 训练 **Stage 1 密度规划模块**，验证段落边界预测准确率。

### Phase 2：核心生成突破（3-8 个月）
- 训练 **AR Transformer Decoder** (12层)，在 50K 谱面数据上跑通自回归生成。
- 集成 RAG 检索模块，实现“参考风格迁移”基础功能。
- 输出首版可玩的 `.osu` 谱面，进行内部人工盲测（对比基线）。

### Phase 3：对齐与产品化（8-12 个月）
- 从 osu! 排行榜抓取玩家评分数据，构造 DPO 偏好对，微调模型。
- 实现 **Flow Matching 蒸馏**，将推理速度降至 < 2秒/首。
- 开发 Web Demo / API 接口，对外封闭测试。

### Phase 4：生态扩展（12+ 个月）
- 支持 6K / osu!std 模式。
- 引入“谱师风格 LoRA”训练，允许用户训练个人风格模型。

## 8. 选型决策矩阵（总览）

> ✅ 代表主选，⚪ 代表备选，✖ 代表放弃。

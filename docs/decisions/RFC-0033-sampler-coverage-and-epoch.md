# RFC-0033 — 采样器覆盖率缺陷与 epoch 定义

- 状态：**采纳**（2026-09-27 由决策者裁定：修采样器 + 定义 epoch + 加覆盖率标量）｜ 提出日期：2026-09-27 ｜ 决定日期：2026-09-27
- 提出者：主会话（训练基础设施 / 数据流水线）
- 影响模块：`beatmorph/infra/train_loop.py`（`ManifestBatchSource` 的取批顺序）、
  `beatmorph/infra/smoke.py`（`coverage()` 的实现）、`beatmorph/data/dataset.py`（新增只读访问器
  `window_row_index`）、plan 07（§3.2 训练入口 / §4.6 日志 / §9）；**不动** plan 00/03/04 的契约与损失

## 背景

本轮（2026-09-27 第八轮）在排查「GPU 长期空转（利用率 21%、功耗中位 7 W）」时，
对数据管道做了剖面（`scripts/local_profile_dataset.py`，cProfile，真实窗口）：

| 函数 | 占每窗口 CPU | 说明 |
|---|---|---|
| `line_tracks_at` | **52.5%** | 逐点线性扫描事件轨：1.46e6 次 `track_value`、**3.97e7 次 `Beat.to_beats()`** |
| 谱面解析 `_chart_for` | 23.8% | json + pydantic 关键帧 |
| 特征加载 `_embedding` | 9.5% | npz deflate |
| 其余 | 14.2% | 建场 / 子谱 / 遮盖 |

修掉第一项（**逐位等价**的向量化定位，见 plan 07 §9-38）后每窗口 **1.218 → 0.582 s**。

**但剖面顺带暴露了一个严重得多的问题。** 为了判断「chart LRU 该开多大」，我模拟了真实取批顺序，发现 **20,000 步只用到 674 个不同的谱面**。随后用**仓库里那份 `_draw` 本身**（只把样本构建换成 stub）复核：

| 步数 | 抽到的不同窗口 | 不同谱面 |
|---|---|---|
| 100 | 100 | 82 |
| 1,000 | **993** | **674** |
| 3,000 | **993（不变）** | **674（不变）** |
| 20,000 | **993（不变）** | **674（不变）** |

**根因**（`ManifestBatchSource._draw`，修复前）：

```python
bucket = buckets[self._bucket_cursor % len(buckets)]
take = min(size, len(bucket))
start = self._cursor % len(bucket)          # 只有一个全局游标
indices = [bucket[(start + offset) % len(bucket)] for offset in range(take)]
self._cursor = (start + take) % len(bucket)
```

游标是**全局共享**的，而它每步都被写成「按**当前桶**长度取模」的结果。桶大小极不均
（min **1**、中位 66、max 35,751），只要撞到长度 1 的桶，游标就被清零 ⇒ 它永远在
「每个桶的前几个窗口」之间震荡，1000 步后彻底饱和。

**后果**：`max_steps` 从 20,000 加到 600,000 **也不会见到任何新数据**。
所谓「全量大规模训练」实际只在 **0.156% 的窗口 / 10.2% 的谱面**上训练，而 loss 曲线
完全正常（它只是反复拟合同一小撮样本）。这与 [POSTMORTEM-2026-08-05] 的 25 Hz 事故同类：
**一个不被任何指标观测的静默失效**。

**为什么没被发现：因为项目没有 epoch 概念。** 没有任何一个数字在回答「这一轮走了多少数据」。
`optim.val_every` 是空转的（val 路径未实现），`run.save_every` 只与步数挂钩。

## 提议

### 1. 取批顺序：每桶独立游标 + 桶内种子化洗牌 + 按剩余窗口数加权选桶

- **每桶独立的抽签顺序**：`_orders[b]` = 该桶窗口下标的一个排列，种子由 `(run seed, epoch)` 派生 ⇒ 同 seed 逐位可复现（M7.8）。
- **每个桶有自己的游标** `_positions[b]`，互不干扰 ⇒ 长度 1 的桶不再破坏别的桶的进度。
- **选桶按剩余窗口数加权**，而不是简单轮转：轮转让每个桶每次 sweep 各拿 1 个，于是小桶被整桶抽干、大桶只被抽走 0.06%；而桶是按 `bpm_eff` 分的，**BPM 常见的大桶恰好装着最多的谱面**。实测：轮转 20,000 步只覆盖 3,122/6,614 张谱面（47.2%），按窗口均匀应当是 ≈91%。加权后实测 **6,036/6,614（91.3%）**，与理论值 91.1% 一致。
- `want`（= 本批样本数）优先：只要还有桶的剩余 >= want，就只在那些桶里加权选，免得一个只剩 1 个窗口的桶把 16 样本的门禁批切成 1（`collate_field_batch` 要求同批同网格）。

### 2. epoch 与覆盖率的定义

- **一个 epoch = 走遍全库、每个窗口恰好被抽一次**：桶内洗牌 + 加权选桶 ⇒ epoch 内是全库窗口的一个**排列**（不是「抽 N 次」的近似）。
- **window_epoch = len(dataset)**（train split = **634,952** 步）。
- **覆盖率标量**（新增，进 `logs/loss_history.jsonl` 与 TB）：`epoch` / `coverage/windows_seen` / `coverage/charts_seen`（累计去重，只增不减）。
- **chart_epoch 被否掉**：每张谱面的窗口数分布极不均（均值 96、min 1、中位 90、p90 141、**max 922**），「每谱一个窗口」不是任何一致的量；直接报**谱面覆盖率**才诚实。

### 3. 实测的预算含义（修复后）

| 预算 | window-epoch | 谱面覆盖 |
|---|---|---|
| 6,614 步 | 1.0% | 59.9%（预测） |
| **20,000 步（当前配置）** | 3.15% | **91.3%（实测）** |
| 50,000 步 | 7.9% | 99.0%（预测） |
| 634,952 步 | 100% | 100%（≈88 h @0.5 s/步，本机不可行） |

⇒ 真·全量 epoch 在 8 GB 笔记本上是 88 小时级、不可作为日常单位；**20,000 步 ≈ 3% window-epoch 但 ≈91% 谱面覆盖**，是一个说得过去的训练预算。

## 备选方案

1. **只把共享游标改成每桶独立游标**（不洗牌、不加权）：覆盖率不再饱和，但采样**有偏**（每桶只取固定的前 k 个，且小桶被过度抽样）。实测 20,000 步仍只有 47% 谱面覆盖。不采用。
2. **全局洗牌流 + 按网格分组**：epoch 语义最干净（严格排列），但多样本取批（门禁要 16 个）会因为相邻条目几乎不同网格而退化成 batch=1。不采用（会动门禁的可信度）。
3. **谱面分层采样**（每谱每轮抽固定个数的窗口）：谱面覆盖最均匀，但改变了「按窗口均匀」的样本权重，且与「一个 epoch = 一个排列」的定义冲突。**留作后续可选**。

## 后果

- **护栏**：`tests/unit/infra/test_sampler_coverage.py`（6 项）钉死「epoch 内每个窗口恰好一次 / 覆盖率只增不减 / 同 seed 可复现 / 选桶按剩余加权 / 同批同网格」。这条护栏是必须的——旧写法**不报任何错**，只是永远重复同一小撮样本。
- **在线可观测性**：覆盖率三项进 jsonl + TB；此后「采样器饱和」这类失效不会再无声存活。
- **已作废的历史结论**：本轮之前所有真实数据训练实跑的**数据覆盖**描述都按本文修正（loss 曲线本身没错，但它是在 993 个窗口上得到的，不能当作「全库训练」的证据）。第五轮 ~2305.8 s 的门禁记录**不受影响**：门禁只取 1-16 个样本且每次新建 source，未触及饱和。
- **重跑门禁是必须的**：取批顺序属训练语义，采样器一变，G1-G4 的批与之前不同（随 `--gates` 启动顺带完成，不额外占 GPU）。
- `data.chart_cache_size` 维持 8：实测 LRU 命中率上限只有 18.6%（同谱复用间隔中位 991 步），调大它不划算——真正的墙是「每窗口重解析一遍谱面」，属下一轮的结构性优化（见 plan 07 §9-38）。

## 本 RFC **不**决定的两件事

1. **是否把训练预算从「步数」改成「epoch 数」**（例如 `optim.max_epochs`）：本 RFC 只把 epoch 变成**可观测量**，不改配置语义（`max_steps` 仍是唯一预算入口）。
2. **是否采用谱面分层采样**（备选 3）。

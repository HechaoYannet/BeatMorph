## 1. 三个质问，逐条正面回答

### 1.1 「项目自己实现了一个问题百出的训练管线？」

**在数据供给这一环：是，而且是设计失败。** 需要把话说准，不能含糊：

- 训练栈的**其余部分**（契约、损失、G1-G4、checkpoint 与旋转、`--resume` 三项校验、
  覆盖率标量、显存墙）都有测试与实跑证据；
- **数据供给这一环**是从「CI 冒烟用的最小参考循环」长成生产路径的，却保留了原型形状：
  `train()` 主循环里**同步**调用 `source.batch()`，**没有任何重叠**。实测 GPU 利用率
  **中位 5.0%**、功耗只有上限的 **18.6%**（21.4 W / 115 W）——**一半以上的墙钟，GPU 在等 CPU**。

所以「数据处理在主线程、等 GPU 算完才开始处理下一批」**是彻头彻尾的设计失败**，
不是「还有优化空间」。这一点你是对的。

### 1.2 「为什么需要这些意义不明的设计？」

因为**三个真实约束被实现成了同一个对象的内部状态**：

| 真实约束 | 错误的落点 | 应该在的位置 |
|---|---|---|
| `FieldBatch` 只带一个网格身份 ⇒ 同批必须同桶 | 采样器内部持有桶与游标 | **计划层**（顺序问题） |
| 同 seed 逐位可复现（M7.8） | 推断成「必须进程内串行取样」 | **计划层**（顺序 = (seed, epoch) 的纯函数） |
| 覆盖率必须在线可见（RFC-0033 的教训） | 在取批过程中**就地累加** | **计划层**（前缀的纯函数） |

三条全是**顺序与记账**问题，却被塞进了「取批」这个**有状态且昂贵**的对象。于是「必须串行」
看起来成了内在要求——它不是，它只是这个耦合的副产品。这也是为什么修一个地方会牵出另一个：
它们本来就不该在同一个对象里。

### 1.3 「为什么不用现成的 torch 管线？」

**可以用，而且重构后就该用。** 现在不能直接开 `num_workers` 的原因恰好三条，
全部来自上面那个耦合：

1. **顺序由采样器内部状态决定**（`_pick_bucket` 读 `self._positions`）⇒ worker 各持副本，
   谁取哪个窗口不确定；
2. **覆盖率在采样器里就地累加**（`self._seen_windows`）⇒ worker 各记一份，
   `charts_seen` **静默失真**，正是 RFC-0033 刚修掉的那类失效；
3. **LRU 是进程内状态** ⇒ N 个 worker 就是 N 份缓存，而命中率封顶 18.6%（同谱复用间隔中位 991 步）。

第 1、2 条搬到计划层后**直接消失**；第 3 条由「桶内按谱聚簇」从根上解决。三者都不是
torch 的限制，是我们把顺序/记账放错了地方。

## 2. 目标架构：三层，各只做一件事

```
L1 计划层（主进程 / 串行 / 纯函数 / 无 I/O）
   plan_epoch(dataset, seed, epoch) -> WindowPlan
     ├ 分桶（沿用现有 grid_key 分桶）
     ├ 桶内按「谱面行」聚簇：同一行的窗口在顺序上相邻
     ├ 行序按 (seed, epoch, 桶key) 种子化洗牌
     ├ 按「剩余窗口数加权」选出每一步的桶（RFC-0033 的公平性原样保留）
     └ 一次性物化 order: int64（train split 一个 epoch = 634,952 → ~5 MB）
   ⇒ 覆盖率 = order 前缀的纯函数，由主进程计算，worker 完全不参与

L2 物化层（worker 进程 × N / 纯函数 / 无共享状态）
   ChartPairDataset.__getitem__(index) -> PairSample     （已经是纯函数：同 index 逐位一致）
   collate_field_batch(samples)         -> FieldBatch    （已经是模块级纯函数、可 pickle）
   ⇒ worker 只回答「这个下标对应的样本是什么」，不决定取哪个下标

L3 搬运层（主进程 / 与 GPU 计算重叠）
   DataLoader(dataset,
              batch_sampler=PlanBatchSampler(plan, start_step),
              collate_fn=collate_field_batch,
              num_workers=N, prefetch_factor=K,
              persistent_workers=True, pin_memory=True)
   ⇒ 主进程只做 H2D + 前向 + 反向；GPU 算当前批时，worker 已在构造成下一批
```

接口（实现以此为准）：

```python
# beatmorph/data/plan.py（新）
@dataclass(frozen=True, slots=True)
class WindowPlan:
    order: NDArray[np.int64]           # 长度 = 本 epoch 的窗口数；桶内连续、桶内按行聚簇
    bucket_of_step: NDArray[np.int64]  # 平行数组：每一步属于哪个桶（诊断/断言用）
    n_windows: int
    n_charts: int

def plan_epoch(dataset: ChartPairDataset, *, seed: int, epoch: int) -> WindowPlan: ...

class PlanBatchSampler(torch.utils.data.Sampler[list[int]]):
    """把 plan 切成 batch_size 的连续片段；start_step 支持续训（从第 start_step 步起）。"""
    def __iter__(self) -> Iterator[list[int]]: ...
    def __len__(self) -> int: ...

def coverage_at(plan: WindowPlan, step: int, batch_size: int, dataset) -> dict[str, float]:
    """order 前缀的纯函数：windows_seen / charts_seen / epoch。**不依赖任何进程状态**。"""
```

## 3. 为什么「谱面解析一次」不再是需要单独论证的补丁

桶内按**谱面行聚簇**之后，同一张谱的窗口在顺序上**相邻**（同一行平均 **96** 个窗口）。
`chart_cache_size=8` 的 LRU 命中率从**实际上的上限 18.6%** 变成接近 100%，
于是「每个窗口重解析整张谱面」（占每窗口 CPU 的 **≈46%**）**自然消失**。

这不是「新增一个缓存」——是**取批顺序**的副产物。v1 之所以要把它当独立方案论证，
正是因为顺序被锁在采样器内部、没法从外面调整。

## 4. 显存与内存纪律（逐条对应已经发生过的事故）

| 历史事故 | 本设计的对应位置 |
|---|---|
| **K² 注意力显存墙**（RFC-0032；旧写法让每条线 attend 全部 K 条线，8 GB 卡 K 上限 ≈31） | **完全不碰模型与批形状**：`batch_size=1` 不变、bf16 不变、本线轨不变；并行只加在 **CPU 进程**上 |
| **8 GB 卡滑进 Windows 共享内存 ⇒ 单步放大 15×**（第五/七轮） | **预取只落在主机内存**：worker **不建 CUDA context、不 import torch.cuda 分配**；GPU 上**同时只有一个 batch** |
| **TDR 事故**（无界 GPU 扫批触发驱动重启） | **不新增任何 GPU 侧预取或扫批**；`prefetch_factor` 只管主机队列，与 GPU 无关 |
| — | **主机上界可算且必须写进代码**：单样本 ≤ ~13 MB（K=128 的 counts）+ 0.4 MB 音频（T=192×1024 fp16）；N=3、`prefetch_factor=2` ⇒ 在飞 ≤ 6 个样本 ⇒ **≤ ~250 MB**；worker 私有 LRU ≤ `feature_cache_size(2) × ~50 MB = 100 MB/worker ` ⇒ < 400 MB |
| — | **CPU 线程预算**：24 逻辑核；单进程实测已占 **6.45** 核（BLAS 多线程）⇒ worker 必须显式 `OMP_NUM_THREADS=MKL_NUM_THREADS=2`，N=3~4 ⇒ ≤12 线程，留余量给主进程与 pinner |
| — | 巡检新增：worker 数、主机内存、峰值显存**同批同 K 与旧管线的差值**（差 > 50 MiB 即告警） |

## 5. 可复现性与续训——**不需要重跑门禁，不需要重建索引**

- **顺序**：`plan_epoch` 是 (dataset, seed, epoch) 的纯函数 ⇒ 同配置两次运行逐位一致（M7.8 不变）。
- **样本内容**：`__getitem__(index)` 本就是纯函数（同 index 两次取值逐位一致，已有契约）。
- **`data.workers` 是语义无关字段** ⇒ 进 `RESUME_IGNORED_KEYS`，理由与 `run.save_every` 同类：
  它不改变实验语义，只改变跑多快。**这同时保证正在跑的这一轮在改动后仍能 `--resume latest`**
  —— 存盘指纹里根本没有这个键，忽略它之后键集与旧指纹一致（须有测试锁定）。
- **索引缓存**：`t_window=192` / `x_bins=128` / `tau_end_policy=audio` / 清单 stat 全不变
  ⇒ `_plan_fingerprint` 不变 ⇒ 现有 **12.1 MB** 的 `.dataset_index/*.npz` **原样复用**，
  一次重建都不会发生。
- **门禁**：损失 / 目标 / 网格 / 遮盖一律不动；**门禁路径不迁移**（继续走
  `ManifestBatchSource.batch(samples=N)`、workers=0）⇒ 既有 `gates.txt` 继续有效。

## 9. 开放问题（不假装已知）

1. **桶内聚簇会不会伤 SGD 的每步多样性**（同谱相邻窗口高度相关）——S4 后可用「同谱窗口是否
   落在同一步」与 loss 曲线的联合观察回答，但**没有对照实验就只是观察，不是结论**。
2. **N 与 BLAS 线程的最优点未实测**（24 核，单进程已用 6.45 核）——S3 后扫 N ∈ {0,2,3,4} 各 200 步。
3. **Windows spawn** 下每个 worker 重新 import torch（启动秒级 + 内存）——`persistent_workers=True`
   摊薄；门禁/冒烟路径**必须**保持 workers=0，否则小配置会被 worker 启动成本主导。
4. **`np.memmap` 旁路**在异常退出时的残留语义（计数可能少记几个）——只影响诊断计数，
   不影响训练；需要在文档里写明而不是假装它是精确的。

### S4 的第一版设计是错的，并被实测抓住

v2 草案把「块」按 `桶偏移 + 块序` 排序（桶按**窗口数**分槽位）。真实 train split 实测
（991 桶 / 634,952 窗 / 6,614 张谱）：

| 口径 | 6,600 步 | 13,200 步 | 20,000 步 |
|---|---|---|---|
| 修复前的均匀撒点（RFC-0033 记录） | — | — | **6,036/6,614 = 91.3%** |
| **S4 v2 草案（按窗口数分槽位）** | 28.3% | 42.9% | **52.6%** ❌ |
| **S4 落地（全局按轮次发牌）** | **71.8%** | **100.0%** | **100.0%** ✅ |

根因：按窗口数分槽位时，「窗口多、谱面少」的桶（例如 1 张谱 10 万窗）会把大量槽位反复花在
同一张谱上，同时饿死窗口少的桶。改为**按轮次**（第 k 轮访问每个桶的每个行恰好一次）后，
「全部谱面各访问一次」只需 Σ_桶(行数) 个槽位，覆盖率因此**严格优于**修复前。

**代价与现状**：`chunk=1`（默认）下同谱连续段中位长度为 **1** ⇒ **没有**摊薄解析的效果
（那 46% 仍在），S4 这一轮拿到的是**覆盖率**而不是解析摊薄；块长大于 1 才摊薄，但会把
「全部谱面轮一遍」的步数放大 `chunk` 倍。是否值得，取决于 S3 并行之后**还差多少**——
这正是步时拆分（§C）要回答的，也是 §9-1 仍未实测的那一项。

## 11. 更正与真实瓶颈（2026-09-27 第十轮）

§10 的验收把 `perf/data_share` 的**中位**当成了结论。**这是错的**：该分布极端重尾，中位与均值
差 10 倍，而决定吞吐的是均值。本轮用三种互相独立的量具重测，并把利用率真正修了上去。

### 11.1 三个量具（互相独立，读数一致）

| 量具 | 读数 | 说明 |
|---|---|---|
| `data_time_s` **分布** | 均值 **0.125 s = 墙钟 45.0%**（中位仅 0.0043 s）；前 10% 的步吃掉 **77.4%**、前 1% 吃掉 **23.6%** | 中位与均值同时为真 |
| `nvidia-smi` 200 ms × 750 | **均值 44.3% / 中位 47.0%**；**42.7% 的采样 ≤5%（完全空转）**、23.3% ≥90% | 强双峰＝有活就满载、没活就全空 |
| `py-spy dump` × 70 | **45.7%** 停在 `wait(threading.py:331)` ← `_try_get_data` | 主线程在 **worker 队列**上等 |

⚠️ **两个量具陷阱，都已踩过并记录**：

1. **PowerShell 管道会缓冲原生命令输出** ⇒ `nvidia-smi --loop-ms` 进 `ForEach-Object` 一条样本都
   收不到（第一版脚本空转 4 分钟、CSV 0 行）。必须用 Python `Popen` 逐行读。
2. **`py-spy record` 在 Windows 上静默丢样本**：80 s@100 Hz 只拿到 4501 个，其叶帧统计把数据等待
   报成 **0.2%**——与 dump 的 **45.7%** 直接冲突。**长跑诊断只用 dump（快照）。**

### 11.2 逐项排除：都不是瓶颈

| 嫌疑 | 实测 | 结论 |
|---|---|---|
| 盘带宽 | `data/processed` 原始读 **2006 MiB/s**；大文件顺序读 2192 MiB/s | 否 |
| zlib 解压 | npz 压缩比仅 **1.09×**、222 MiB/s ⇒ 每窗口 **106 ms**（占 0.85 s 的 12%） | 否 |
| `pin_memory` 单线程 | 开/关 = 6.33 / 6.34 窗口/s | 否 |
| 主进程 CPU | **0.05 核** | 否 |
| BLAS 过度订阅 | OMP=1 与 =2 = 6.31 / 6.33 | 否 |
| Defender 实时扫描 | 本就关闭 | 否 |

### 11.3 真实瓶颈：整谱工作被按窗口重复

标定曲线（`scripts/local_worker_scaling.py`，真实 train split、只改 `data.workers`、逐臂断言索引
缓存命中）：**2.51 / 4.42 / 6.33 / 5.75 / 6.28 窗口/s @ N=3/6/8/10/12** ⇒ **N≥8 起封顶**，而训练需求
约 11.5 窗口/s。单进程每窗口 **0.85 s**：谱面解析 ≈**44%**、建场 ≈**33%**、特征解压 ≈**12%**。

根因是本设计**自己的顺序**：计划层跨 **991 个桶**轮转发牌，一张谱的 ~96 个窗口落在相隔 ~991 个槽位
上 ⇒ 任何 LRU 都必然不命中（`chart_cache_size=8` / `feature_cache_size=2` 形同虚设），**同一张谱
在一个 epoch 里被完整重解析 96 次**。这正是 RFC-0033/0034 换来覆盖率所付的代价。

### 11.4 已修：N=3 → 8（纯配置）

同分布段间实测（`--resume latest` 从 step 16000 起；索引缓存命中、**未跑门禁**、指纹通过）：

| 口径 | workers=3（14000–16000） | **workers=8（16201+）** |
|---|---|---|
| GPU 利用率 均值 / 中位 | 44.3% / 47.0% | **75.5% / 80.0%** |
| GPU 完全空转（≤5%）占比 | 42.7% | **9.5%** |
| `perf/data_share`（按和） | **46.4%** | **22.4%** |
| 步时 mean / p90 | 0.296 / 0.732 s | **0.195 / 0.347 s** |
| data 等待 p90 | 0.451 s | **0.0118 s（38×）** |

**跑完全段（steps 16201–20000，n=4050）后 `perf/data_share` = 19.0% ⇒ 判据 3a（<20%）也达标**（上面表里的 22.4% 是 16201–17800 的部分段；全段步时 mean 0.1994 s、K 中位同为 26 ⇒ 不是 K 分布变简单）。

### 11.5 开放问题（更新 §9）

1. **尾部仍在**：p99 1.68 s；一个 worker 卡一次能拖穿 16 个预取槽 ⇒ 加深预取（`prefetch_factor`）
   或削掉整谱重复。**两者都要先量再改。**
2. **内存是硬上限**：`commit charge` 已达 **38.1 / 40.1 GiB（95%）**（物理 31.4 GiB，页文件约 8.7 GiB）
   ⇒ **N=8 同时是内存拐点**，再加 worker 会踩页文件；任何「加 worker」方案必须先算内存账。
3. **削整谱重复会动取批顺序语义**（局部性 vs 每步谱面多样性，正是 §10 里 S4 第一版翻车的那条线）
   ⇒ **必须先开 RFC，不得在配置里悄悄改**。

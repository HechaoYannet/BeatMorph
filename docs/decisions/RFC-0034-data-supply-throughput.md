# RFC-0034 — 数据供给吞吐：消除逐窗重解析，并给出预取的边界

- 状态：**提案**（待决策者裁定 A / A+B）｜ 提出日期：2026-09-27 ｜ 决定日期：待定
- 提出者：主会话（训练基础设施 / 数据流水线）
- 影响模块：`beatmorph/data/dataset.py`（谱面解析与窗口切片的缓存形态）、
  `beatmorph/infra/train_loop.py`（`ManifestBatchSource` 的取批路径）、plan 02 §3 / §9、
  plan 07 §4.5 / §9；**不动** `core/contracts`、网格口径、损失与取批顺序语义

## 背景

触发问题（决策者，2026-09-27 第九轮）：**「当前 GPU 的平均占用率依然不算高，是不是 workers 太小了？」**

实测（训练进行中，`runs/phigros_masked/20260927-100604`，step 1850/20000；RTX 5070 Laptop
8 GB / 功耗上限 115 W）：

| 指标 | 实测 | 读法 |
|---|---|---|
| GPU 利用率（1 Hz × 60 采样） | 均值 **35.7%**、**中位 5.0%**、p90 100%、**29/60 采样 ≤1%** | **双峰**：要么满载、要么空转；中位 5% 说明一半以上时间 GPU 什么都没干 |
| GPU 功耗 | 均值 **21.4 W** / 上限 115 W（**18.6%**），峰值 78.3 W | 卡基本没被用起来 |
| 训练进程占用核数 | 均值 **6.45** / 24 逻辑核，峰值 14.89 | CPU 侧**确实**在多核跑（numpy），但关键路径是串行的 |
| 系统 CPU | 均值 30.1%、峰值 62.8% | 整机没满 |
| 显存 | 7862 / 8151 MiB = **96.4%** | 8 GB 卡的已知常态（plan 07 §9-35） |
| 步时 `step_time_s`（1850 步） | 中位 **0.539 s**、均值 0.871、p90 1.721、p99 4.52、max 6.83；**478/1850（25.8%）≥1 s** | 长尾 |
| 批的 K | 中位 26、p90 67、max 128 | 长尾来自 ∝(K·T)² 的注意力 |

**关键事实：训练路径里根本没有 worker。** 全仓 `grep num_workers` 只命中**数据准备**脚本
（`scripts/fetch_phira.py`、`scripts/extract_features.py`）；训练侧唯一的 torch DataLoader 在
`beatmorph/infra/lightning_module.py`，且是 `DataLoader(_BatchListDataset(...), batch_size=None)`
（`num_workers` 取默认 0）。真实训练走 `ManifestBatchSource.batch()`，它在**训练进程主线程里
同步**完成「选桶 → 取窗口 → 解析谱面 → 建场 → collate」，而 `step_time_s` 的计时起点在这一句
**之前** ⇒ **数据构建时间被算进了步时**。

所以「workers 太小」这个旋钮**当前并不存在**。但这不等于提问错了：GPU 中位 5% 的空转，
方向确实是「数据侧供给」，只是可行的修法不是把 `num_workers` 调大。

## 根因

### 1. 每个窗口都要重解析整张谱面（每窗口 CPU 的 ≈46%）

`ChartPairDataset.__getitem__` 每次取一个窗口都会为该窗口**重新解析所属谱面**
（json + pydantic 关键帧），没有跨窗口的谱面级缓存复用。而一张谱平均有 **96 个窗口**
（min 1 / p25 70 / 中位 90 / p75 112 / p90 141 / max 922）⇒ 同一张谱被解析几十到几百次。

上一轮把 `line_tracks_at` 向量化后每窗口 CPU 从 1.218 s 降到 **0.582 s**，谱面解析的相对
占比随之升到 **≈46%**——它现在是数据侧第一大项，此前被更大的那一项遮住了。

### 2. 把 `num_workers` 调大**不会**修好它，反而先坏两件事

- **缓存是进程内的**：chart LRU 与 feature LRU 都活在 `ChartPairDataset` 实例里。N 个 worker
  = N 份缓存副本（内存/显存按 N 倍涨），而命中率不会按 N 倍涨。
- **而缓存本来就不是解法**：chart LRU 命中率实测封顶 **cap=8 → 18.6%、16 → 23.3%、
  32 → 26.1%、64 → 28.7%**。原因是取批顺序按 `bpm_eff` 分桶且桶内逐 epoch 洗牌，
  **同一张谱的窗口在顺序上不相邻**（同谱复用间隔中位 **991 步**）。`chart_cache_size`
  从 8 调到 64 只值 +10 个百分点。

### 3. 串行决策点在「选桶」，不在「取样本」

取批顺序是**有状态**的：每桶独立游标 + 每 epoch 洗牌 + 覆盖率记账（[RFC-0033]）。torch 的
DataLoader worker 只并行 `__getitem__`，**不并行**「选哪个桶 / 哪个窗口」这个串行决策点；
而覆盖率记账（`windows_seen` / `charts_seen` / `epoch`）落在主进程，worker 各持一份
副本会让它**静默失真**——正是 RFC-0033 刚修掉的那一类静默失效。

### 4. 步时长尾是 K²，与数据侧无关

K 中位 26 / p90 67 / max 128，单步注意力代价 ∝(K·T)²。这解释了均值为何被拉高：
**p90 以上的少数步把 GPU 打满几秒，中位步只占 GPU 几十毫秒，其余时间都在等 CPU。**
（门禁 36.5 min 的预算也是同一个 K² 规律，见 plan 07 §9-41。）

## 提议

### A. 结构性（建议先做）：谱面解析一次，窗口切片多次

把「解析谱面 → 得到该谱全部窗口的场」变成显式的**按谱缓存 + 一次解析出多窗复用中间量**，
代价从 O(窗口数) 降到 O(谱面数)。可行形态（择一，实现时定）：

- **A1. 按谱懒加载**：首次访问某谱时解析一次，缓存**窗口可复用的中间量**（关键帧求值、
  判定线几何、BPM 段），窗口索引只做增量切片。与取批顺序**完全解耦**。
- **A2. 批次按谱聚集**：取批时优先取同一张谱的多个窗口，把一次解析摊到 N 个样本上。但
  `FieldBatch` 要求同网格身份 ⇒ 同一谱内跨 BPM 段的窗口不能同批，需按谱内 BPM 段再分桶；
  且这会**改变批的构成**（影响梯度统计），须单独论证。

预计收益（A1）：每窗口 0.582 s → ≈0.31 s，2 万步墙钟约 4.9 h → ≈3 h（K 分布不变前提下）。
**且不引入任何并发 ⇒ 可复现性零风险。**

### B. 预取的边界（A 之后再评估，且**必须有界**）

只有在 A 落地后若仍有 >30% 的步时被数据侧占据，才加**有界**预取：队列深度 1–2，生产者
**只做样本构建、不做选桶**（选桶仍留在主进程串行，保证覆盖率记账与同 seed 可复现）。

**必须写明的前车之鉴**：本项目已在 `scripts/extract_features.py` 实现过预取（`--pipeline`），
基准 **2.85×**，但**首次上生产就挂住**（CPU 满载 1 核 / GPU 0% / 数分钟无输出）。根因是回压
循环 `while len(self._order) >= self._depth: self._futures[self._order[0]].exception()`
**从不把最老的一项移出窗口**（条件恒真、死循环空转），外加补窗下标 off-by-one。见 plan 02 §9。
⇒ **无界/无回压预取在本项目已出过一次事故，故此案只允许有界，并必须带「慢消费者下队列不
无界增长」的单测。**

### C. 观测（本轮已落地，指向 plan 07 §9-42）

`step_time_s` 拆成 `data_time_s` + `compute_time_s`（逐行和恒等于步时），TB 增
`train/data_time_s`、`train/compute_time_s`、`perf/data_share`，巡检脚本
`scripts/training_health.py` 打印拆分并在**数据占比 ≥50%** 时告警。

**理由**：本轮之所以要花一整轮去「猜」瓶颈在哪一侧，正是因为一个数把两件事混在了一起；而
「猜」的代价上一轮已经付过——把 38 min 的正常门禁误判成卡死并掐了两次（plan 07 §9-41）。

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 直接 `DataLoader(num_workers=4)` | 每进程一份 LRU 缓存（内存 ×4、命中率不涨）；选桶串行仍在主进程；覆盖率记账在 worker 副本里**静默失真**（RFC-0033 同类失效） |
| 只调大 `chart_cache_size` | 已实测无效：命中率封顶 18.6%（cap=8）→ 28.7%（cap=64），同谱复用间隔中位 991 步 |
| 加卡 / 开更大 batch | 瓶颈不在 GPU（功耗仅到上限的 18.6%）；`batch_size` 受 K² 显存墙限制，8 GB 卡已 96.4% |
| 降 `t_window` / `x_bins` 换吞吐 | 改网格口径 = 改数据契约与训练语义，代价远超收益 |
| 不修，只让本轮跑完 | 本轮作为首次全量端到端验证仍有价值；但跑完不修，下一次仍是同一堵 2× 墙钟 |

## 后果

- 采纳 A1：每窗口 CPU 预计 0.582 s → ≈0.31 s；不改 `core/contracts`、网格口径、损失与
  取批顺序语义，**可复现性不受影响**（无并发）。
- 新增回归测试：同一谱的多个窗口在「缓存一次」路径与「逐窗重解析」路径下**逐位一致**
  （沿用 RFC-0033 的判据：`torch.equal`）。
- 若同时做 B：须补「慢消费者下预取队列不无界增长」的护栏测试（复现旧 `--pipeline` 死循环）。
- **门禁不需要重跑**：本项不改损失/目标/网格，只改**取样本的代价**；但首轮实跑建议仍走
  `--gates` 以保持流程一致。

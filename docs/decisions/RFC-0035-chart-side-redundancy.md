## 1. 问题（全部为实测值，不引用估计）

第十轮把 GPU 利用率量准了：**44.3%**（200 ms × 750 样本），其中 **42.7% 的采样完全空转**；
主进程主线程 **45.7%** 的时间停在 `_try_get_data`（等 DataLoader worker）。把 `data.workers`
从 3 提到 8 之后（跑满到 step 20000）：GPU 利用率 **75.5%**、`perf/data_share` **19.0%**、步时 mean **0.199 s**。

**剩下的 19.0% 仍然全在数据侧。** 数据侧的成本结构已由**函数级 cProfile** 量出
（`scripts/local_build_split.py`，真实 train split 100 个窗口，`workers=0`，只取 `_build_sample`
下**互不包含**的顶层调用，cumulative 可加）：

| 顶层调用 | 占每窗口 CPU | 属于 | 说明 |
|---|---|---|---|
| `_read_chart_or_skip` | **49.1%** | **全谱** | 其中 `parse_rpejson` **48.2%**（`read_bytes` + `json.loads` + pydantic） |
| `_window_subchart` | **23.6%** | **全谱** | 其中 `_note_bins` **23.5%**——**线性扫过全部 1,294 个 note 只挑出窗内的约 13 个** |
| `load_feature_cache` | **15.6%** | **全谱** | 每窗口读 **11.3 MB** `savez_compressed` 整段解压；压缩比仅 **1.09×** |
| `line_tracks_at` | 3.0% | **全谱** | |
| `FieldGrid.for_chart` | ~0% | 全谱 | BPM 点很少，本来就便宜 |
| **全谱工作合计** | **91.3%** | | **一张谱只该做一次，却被 96 个窗口各做一遍** |
| `build_occlusion` | 5.9% | 逐窗口 | |

单进程每窗口 **0.85 s** ⇒ **其中约 0.78 s 是「同一张谱的第 2..96 次重复劳动」。**
**一张谱在一个 epoch 里被完整重建 96 次。**

## 2. 为什么现有旋钮都拧不动（逐条算术否决）

### 2.1 「把缓存调大」——**工作集放不下，而且每进程一份**

已解析谱面实测 **18.12 MB/张**（§10.1；median 12.56 / p90 28.1 / max 168）。计划层跨 **991 个桶**
轮转发牌 ⇒ 同一个 worker 再见到同一张谱要等约 **991 个槽位**（实测 W=8 的重访距离 median **2340 张不同谱**）
⇒ 想命中就得常驻 **991 张** = **17.9 GB**。worker 是**独立进程**（Windows spawn），缓存不能共享
⇒ 8 个 worker 要 **143 GB**。本机物理 31.4 GiB、`commit` 已到 **38.1/40.1 GiB（95%）**。
**这条路是死的**，不是「再调大一点」。**实测的 LRU 曲线把这一点钉死**：C=8 → 命中率 **0.35%**、
C=1024 → 23.24%、要 50% 需 **72.5 GiB/worker**（8 worker = **580 GiB**）；而且一个 epoch 内命中率
**≤ 1 − 谱面数/访问数** ⇒ **W=8 的结构上限只有 91.67%（W=1 才 98.96%）**，**99% 结构性不可达，
加 worker 反而降低上限**。

### 2.2 「把 `chunk` 调大」——**摊薄解析与「每步谱面多样性」直接对冲**

`chunk=K` 让每个桶每轮发 **K 个连续窗口**（同一张谱）。但 DataLoader 把第 i 个槽位发给第
`i % W` 个 worker ⇒ worker 拿到的仍是被打散的。要让每个 worker 连续拿到同一张谱的多个窗口，
需要 `K ≥ W × (每 worker 连续数)`；而「全部谱面轮一遍」的步数**乘以 K**（`plan.py` 的
模块 docstring 已写明）。真实 train split 实测过这条曲线的另一端：**S4 第一版让 20,000 步只覆盖
52.6% 的谱面**（均匀撒点 91.3%），被实测抓住并改掉。

### 2.3 「把取批顺序改成谱面局部」——同上，且更狠

顺序 = 每张谱连续发完全部 ~96 个窗口。worker 局部性完美（缓存 1 张即可），但**每步多样性 = W**、
**谱面覆盖率 = 步数/96**：20,000 步只覆盖 **208/6,614 = 3.1%** 的谱面。

> **结论**：worker 本地缓存与「每步看到很多不同谱面」是**不可兼得**的。
> 要同时拿到两者，只能让「每张谱的准备工作」**一次做好、放在所有 worker 都能零成本读到的地方**。

## 3. 方案：把谱面侧的派生工作一次性物化，落成可 mmap 的紧凑产物

核心观察：**索引构建期本来就把每一张谱解析了一遍**（`_plan_row` → `_chart_for` →
`_read_chart_or_skip` / `parse_rpejson`，36.5 min 覆盖 8551 张）。现在这份解析结果用完即弃，
训练期再逐窗口重做 96 遍。把它**留下来**即可——但必须留成**紧凑**形式，因为完整对象图 9.79 MB/张。

### M0 谱面内定位：线性扫 → 二分（**最便宜的一项，先做**）

`_window_subchart` 里的 `_note_bins` 是**对全部 1,294 个 note 逐个判定「落不落在本窗口」**，
占每窗口 **23.5%**。同一个仓库里**已经修过一次同类问题**：`line_tracks_at` 原是 1.46e6 次
`track_value` + 3.97e7 次 `Beat.to_beats()`，改成 `searchsorted(starts)` + `prefix_max(ends)`
后每窗口 CPU 1.218 → 0.582 s（**32.9×**）。note 表按「起点格」排好序后同理可二分；
更好的做法是在**索引期**就把「每个窗口 → note 下标区间」算好（索引期本来就遍历过全部 note）。

**收益 ≈23.5%，成本最低（不动契约、不加产物、不动顺序）。**

### M1 特征缓存转码：`savez_compressed` → 无压缩、可 mmap 的 `.npy`

`np.savez_compressed` 在这份数据上压缩比只有 **1.09×**（MERT 特征近似随机，zlib 几乎压不动），
却让每个窗口付出 **106 ms** 的解压 + **11.3 MB** 的整文件读。改成无压缩 `.npy` 后：

- 用 `np.load(..., mmap_mode="r")`，**只触达窗口需要的那几十帧**（约 1 MB 页），不解压整段；
- 页缓存**跨 worker、跨 epoch 共享**，重复访问近乎免费；
- 语义**逐位不变**（同一段 float32 字节，只是不再过 zlib）。

成本：特征目录磁盘占用 ×1.09（约 **+105 GB**；D: 盘尚有 **858 GB** 空闲）。转码是一次性离线 pass
（解压一遍再写出，可用 16 进程并行，量级 **10-20 min**），**不需要重抽特征**。

### M2 谱面紧凑包（本文的主方案）

为每张谱写一个**可 mmap 的紧凑旁车**，只装训练路径真正需要的东西：

- note 表：`t / x / type / hold / line_id / …` 定长数组（1,294 note/张 ≈ **31 KB**）；
- 判定线事件轨的**原始关键帧**（不是求值后的稠密轨）；
- BPM 点列、`META`（offset / duration / chartTime）；
- 窗口规划所需的标量。

实测 **685 KB/张**（= 对象图 **3.78%**；note 表 54 KB + 普通轨关键帧 628 KB，`extended` 训练不用）
⇒ 6,614 张 train ≈ **4.5 GB**（对比完整对象图 **117 GiB**）。**仍完全可接受，但比本节原先估的大 3.4–6.9×。**

训练期 `_build_sample` 改为：从 mmap 里**只取本窗口命中的 ~13 个 note** 重建 `PhigrosNote`、
重建本窗口的子谱与 BPM 点 ⇒ `build_target` 照旧。**JSON 与 pydantic 完全退出训练路径**，
9.79 MB 的对象图**不再被构造**。

## 4. 为什么这两个方案不伤害任何已锁定的语义

| 已锁定的语义 | 为什么不受伤 |
|---|---|
| **每个窗口恰好一次 / epoch**（RFC-0033） | 顺序**一个字节都不改**，改的只是「窗口怎么被物化」 |
| **每步谱面多样性**（RFC-0034 §10 的 S4 教训） | 顺序不变 ⇒ 多样性不变 |
| **顺序是 `(seed, epoch, 索引)` 的纯函数** | 不受影响 |
| **`data.workers` 续训中性**（RFC-0034 §5） | 受影响更小：产物与 worker 数**无关** |
| **不重跑门禁** | 门禁路径（`workers=0` + 有界切片）可保持走原解析路径，产物是可选的 |
| **G4 派生常量契约** | 不引入任何新的物理常量 |
| **样本逐位一致** | 必须由测试锁定（见 §6 判据 1） |

## 5. 成本与收益（诚实算术，含「收益其实不大」）

**必须先说清楚上界**：即使数据供给变成无限快，步时也**不可能低于计算段**。
当前 compute mean **0.151 s** vs step mean **0.195 s** ⇒ **端到端最多再快 1.29×**
（GPU 利用率上限从 75.5% 抬到约 95%）。**这一轮之后的主要收益不再是速度。**

按 §1 的实测拆分，三项措施各自消掉哪一块、需要多少 worker 才能喂饱
（需求约 **11.5 窗口/s** = 计算段中位 0.087 s 的倒数）：

| 措施 | 消掉 | 每窗口 0.85 s → | 8 worker 供给 | 3 worker 供给 |
|---|---|---|---|---|
| 现状 | — | 0.85 s | 6.3/s（实测，不足） | 2.5/s（实测，远不足） |
| **M0**（note 定位二分） | 23.5% | 0.65 s | 12.3/s ✅ | 4.6/s ❌ |
| **+ M1**（特征转码 mmap） | +15.6% | 0.52 s | 15.4/s ✅ | 5.8/s ❌ |
| **+ M2**（谱面紧凑包） | +49.1% | **≈0.08 s** | — | **≈39/s ✅✅** |

即：**M0+M1 不动顺序、不加谱面侧产物，只把 8 个 worker 的效率提到「刚好够」；
只有 M2 才能把 worker 数降回 3 个。** 而 8 个 worker 正是**被 `commit` 内存逼出来的**（§5 第 1 条）。

M2 真正的价值有三条：

1. **把 8 个 worker 降回 2-3 个**就能喂饱 GPU ⇒ 释放 **≈5-6 GB `commit`**（当前只剩约 2 GiB）
   与 5-6 个核；现在 N=8 是**被内存逼出来的**上限，不是最优点；
2. **数据侧的抗尾能力**：p99 仍有 1.68 s 的等待，削掉整谱工作后单窗口成本从 0.85 s 掉到约 0.35 s，
   尾部按同比例缩短 ⇒ 同样的预取深度能吸收更长的抖动；
3. **为后续扩数据留出余量**：现在「加 worker」已经撞到内存墙。

## 6. 验收判据（可测、可回退）

| # | 判据 | 口径 |
|---|---|---|
| 0 | **先量再建**（见 §7） | 逐窗口成本里「全谱工作」与「逐窗口工作」的**实测**占比；若全谱占比 <50%，**M2 不值得做** |
| 1 | **样本逐位一致** | 同一 index，新路径与旧路径 `torch.equal` 逐位相同（像 RFC-0034 的 workers 等价性那样） |
| 2 | **覆盖率不变** | `charts_seen` / `windows_seen` 与旧路径同步数完全一致 |
| 3 | **吞吐** | `workers=3` 下 `perf/data_share` **< 5%**（当前 19.0% @ N=8）；步时 mean **≤ 0.16 s** |
| 4 | **内存** | `commit` 峰值**下降**（worker 数减半）；峰值显存不变 |
| 5 | **产物可重建且可回退** | 删掉旁车即回到当前路径；旁车由 fingerprint 定位，指纹不符**拒绝使用**而不是静默降级 |

## 7. 判据 0 已实测（本节原计划「先量再建」，量已经做完了）

**全谱工作 91.3% / 逐窗口工作 9.9%**（表见 §1；`scripts/local_build_split.py`，100 个真实窗口，
单进程无 GPU，约 90 s）。判据 0 的门槛是「全谱占比 <50% 则 M2 不值得做」⇒
**实测 91.3%，M2 成立，且富余很大。**

顺带把三件事分出了优先级（§3）：**M0 23.5% 最便宜、M1 15.6% 次之、M2 49.1% 最贵**。
§5 的表给出了每做完一项「8 个 worker 是否够用」的答案 —— **M0 单项就能让 8 worker 从「不足」
变成「刚好够」**。因此建议的实施顺序是 **M0 → 量 → M1 → 量 → M2**，每步独立可回退。

⚠️ **该 profile 口径的两个已知偏差**（不假装它是精确的）：`cProfile` 逐调用有固定开销，
对**调用次数多**的函数（`_note_bins` 1,294 次/窗口、pydantic 内部）系统性偏高；
绝对值应以不带 profile 的 **0.85 s/窗口**为准，本表只用于**归属比例**。

## 8. 不做 / 已否决

- **不把完整 pydantic 谱面做缓存**（§2.1 算术）；
- **不改取批顺序**（§2.2/§2.3：会牺牲每步多样性，且 S4 已经在这条线上翻过一次车）；
- **不重抽特征**（M1 只是转码，不重算 MERT）；
- **不动模型 / 损失 / 网格 / 遮盖 / `batch_size`**；
- **不为了这个动门禁路径**。

## 9. 开放问题（不假装已知）

1. **紧凑包能不能完全避开契约对象**：`build_target` 与 `line_tracks_at` 的签名收的是
   `PhigrosChart`。若「重建窗口子谱」仍要走完整对象构造，M2 的收益会打折——**这是 M2 最大的未知**，
   也是 §7 要先量的原因之一。
2. **Hold 跨窗与事件轨求值的等价性**：`_window_subchart` 的逐格等价性有测试锁定
   （`test_window_counts_equal_full_chart_slice`），紧凑包必须复用**同一**口径，不得另写一套。
3. **M1 的 105 GB 是否值得**：它只消掉 ≈12%，但副作用是页缓存共享与「读得少」。若 §7 显示解压占比
   被低估，M1 的优先级会上升。
4. **旁车与索引缓存的失效关系**：两者都由同一份清单派生，但失效条件不同（索引看 config 指纹，
   旁车还应看谱面文件的 stat）。需要明确「谁失效谁」而不是各自猜。

### 10.2 「扩大缓存」被三条独立实测否证（本文 §2.1 的结论成立，且更强）

1. **容量**：50% 命中率需 **72.5 GiB/worker**（8 worker = **580 GiB**）；90% 需 145 GiB/worker（1160 GiB）。
   本机物理 31.4 GiB、训练时可用余量 ≤ ~10 GiB ⇒ **差 1–2 个数量级**。
2. **结构上限**：一个 epoch 内命中率 **≤ 1 − 谱面数/访问数** ⇒ **W=8 上限 91.67%**（W=1 才 98.96%）
   ⇒ **99% 结构性不可达，而且加 worker 会降低上限**。重访距离实测 W=8 median **2340 张不同谱**
   （全局槽位间隔 median 5917）。
3. **收益**：花 145 GiB 买 ~11% 是纯亏（≈**13–25 GiB / 1% CPU**）。

### 10.3 「共享」只对字节成立（本文 §3 路线选择的机制依据）

6 进程 × 200 MB：私有读 private 合计 **1325 MB（6.62×）** / **mmap 124 MB** / **@@shared_memory@@ 126 MB**；
但**谱面对象图 pickle 给 6 进程照样 +287 MB**（各建一份）。@@torch.Tensor.share_memory_@@ 共享的是
**张量存储**，对 pydantic 对象图**用不上**。⇒ ① 部分可行（**必须先放弃对象图**）｜② **可行且推荐**｜
③ 可行（685 KB/张）｜④ epoch 预热**不可行**（C=P=256 只 +0.32 pp——因为工作集就是全部 6614 张）。

### 10.4 补测 @@chunk@@（本文 §2.2 的量化）

命中率要 **@@chunk ≥ 2W = 16@@** 才起来（**47.5%**），代价是 20k 步谱面覆盖率 **100% → 18.4%**（K=16）
→ **5.1%**（K=96）。**本文「不改顺序」的立场由此得到实测支持。**

### 10.5 M1 的实测支撑（方向写对了，且数字比本文更好）

特征数组 mean **29.2 MiB**，而**每窗口只需要 109.7 帧 = 1.54%（0.22 MB fp16）**；
**npz 暖读 = 冷读（61.9 vs 61.1 ms）⇒ 全是 zlib 的 CPU 成本，与页缓存无关**；转成无压缩 @@.npy@@ +
@@mmap@@ 后取 100 行 **0.034 ms（暖）/ 0.465 ms（冷）** ⇒ 每窗口特征代价 **97 ms → 0.03–0.5 ms**，
且页缓存**跨 worker、跨 epoch 共享**。**M1 完全不需要命中率。**

### 10.6 由此更新的结论

**唯一值得走的路线仍是 M1 + M2（先 M0）**，但：

- **收益按 50.3% 而不是 91.3% 重算**（§5 那张表要重做）；
- M2 的紧凑包按 **685 KB/张（全 train 4.5 GB）** 估；
- M1 + M2 合计把窗口成本压到实测下界 **154 ms**。

**存疑（继承调研的 D1–D9，最要紧的三条）**：

1. **冷成本 0.480 s/窗口 vs 仓库记的 0.85 s 的差异未解释**（差 1.77×）——而本文 §5 的整张表都建在
   「每窗口成本」上 ⇒ **这张表必须在差异解释清楚之后重算，现在不要拿它做决策**；
2. 紧凑旁车的**消费路径尚未实现**，「能否完全避开契约对象」**仍未验证**——这正是本文 §9-1 的未知，
   **现在仍然未知**（M2 的最大风险没有变）；
3. @@mmap@@ **只在机制层面验证过，没有端到端跑过**。
